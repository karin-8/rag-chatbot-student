RAG in Production: A Real-World Implementation of a Customer-Support Chatbot

Design, evaluate, deploy and monitor a retrieval-augmented chatbot using the engineering practices of production AI systems.

Prerequisites
  • Finish Appendix A: Pre-Class Setup at home (about 30 minutes, downloads 1.1 GB).
  • Bring a laptop (Windows or Mac). Tablets cannot run the project; if no laptop is available, use the Codespaces fallback.
  • Get the code: download the ZIP or open github.com/karin-8/rag-chatbot-student.
  1. 1 · Knowledgechunk, embed, store
  2. 2 · Agentprompt + policy
  3. 3 · Testgolden dataset, gate

How to use this guide

  • Every module has a Scenario, Tasks, and the Expected results for each task. Click a task's title to open it, and tick its box when you finish.
  • If you encounter difficulties, open the hints under a task in order. If the issue persists after a few minutes, consult a neighbor or the facilitator.
  • Run code from the project folder with python -m src.<name>, not VS Code's ▶ Run button.

Task 1

Read the Dockerfile and the pipeline

Instructions

  1. Open Dockerfile and read it top to bottom (the comments explain each line).
  2. Open .github/workflows/ci.yml. Find its three jobs, and which of today's commands each step runs.
  3. Answer the questions below, then expand each one to check your answer.
Why are the model weights downloaded when the image is built?

So every container starts instantly and identically, without a 1 GB download that could fail.

Why is requirements.txt installed before the code is copied?

Docker reuses cached layers. Libraries rarely change; code changes frequently. So a code change only rebuilds the last, fast layers.

Which job runs only for changes pushed to main?

deploy. Pull requests stop after build.

Expected results
  • You can name the jobs in order: test → build → deploy.
  • You can match the test job's steps to today's commands: python -m src.ingest, pytest, python -m src.gate.
Task 2

Trace four changes through the pipeline

Instructions

  1. For each change below, decide which job and step stops it (if any), and what customers end up with.
  2. Expand each one to check your answer.
A. A teammate sets PROMPT_VERSION = "v2" and pushes to main.

The quality gate in test fails (out of scope and refund got worse). build and deploy never run, so customers keep v1.

B. Someone deletes "24/7" from data/policies.txt by accident.

pytest fails: the support_hours cases cannot find "24/7". Changes to the knowledge go through the same tests as changes to the code.

C. A typo fix in README.md.

All checks pass and the change is deployed, possibly after a manual approval.

D. v1 is live, and a week later it fails on a new kind of question.

Add the new questions to the golden dataset (they fail), fix the prompt as a new version or fix the knowledge, then push it through the pipeline. Rolling back means redeploying an older image by its commit tag. Never patch production by hand.

Expected results
  • Your answer for each of A–D matches the one inside it.
