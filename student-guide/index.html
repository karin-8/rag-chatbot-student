From Colab to Code: Build Your RAG Chatbot for Real

A 2-hour build workshop. Keep this guide open in one window and VS Code in the other, then work through the modules in order.

Today's mission

Take your Week 5 RAG chatbot and turn it into a real, runnable local application.

  • Required: a CLI you can run and chat with, backed by a real local database.
  • Stretch: a Streamlit interface on top of the same backend.

How to use this guide

  • Each module has outcomes, numbered steps and a checkpoint. Tick steps as you go. Your progress is saved in this browser.
  • Stuck? Open the hints in order: Nudge, then Bigger hint, then Solution. Try for a few minutes before you open the next one.

  • If you're behind a checkpoint, don't troubleshoot alone. Ask a neighbor or the facilitator and keep moving.
  • Hit an error? The Troubleshooting page at the end lists the common ones and their fixes.
  • Before class: complete the Before class module at home. It downloads about 1.1 GB, which won't work on shared classroom Wi-Fi.

RAG in 30 seconds

A small language model doesn't know LumaBox's policies, and if you ask it anyway it will guess. Retrieval-augmented generation fixes that in two stages:

  1. Prepare once. Cut the documents into chunks and turn each chunk into an embedding, a list of numbers that captures its meaning. Store the embeddings.
  2. Answer each question. Embed the question the same way, find the stored chunks whose embeddings are closest (the most similar meaning), paste those chunks into the prompt as context, and let the model answer from that context.

You built exactly this in Week 5 in a notebook. Today you rebuild it as a project, and the embeddings move from a NumPy array in memory to a database on disk.

TODO I2

Chunk the raw text

A chunk is the unit retrieval hands back. When a question comes in, the bot pastes whole chunks into the prompt, so each chunk should be a self-contained piece of evidence.

  • Too big (the whole file): every question retrieves everything, the embedding becomes an average of unrelated topics, and you blow the model's 512-token prompt limit.
  • Too small (one line each): the line "Available 24/7, every day." gets separated from its heading, "Technical Support", and on its own it doesn't say what is available.

This file has a clear structure, one policy per paragraph, so splitting on that structure gives ideal chunks. For long unstructured text (a PDF manual, say) the usual fallback is fixed-size chunks of a few hundred words with some overlap between neighbors.

Open data/policies.txt and look at its shape. Then fill in chunk_documents() so it returns a list of chunk strings.

  • Policies are separated by blank lines.
  • Strip whitespace from each piece.
  • Drop the title line at the top. It's a heading with no body.
Nudge Level 1

DATA_PATH.read_text(encoding="utf-8") gives you the whole file as one string. A blank line is "\n\n".

Bigger hint Level 2

A real policy chunk has a heading line and a body line, so it contains a newline. The title line doesn't. Use that to filter.

TODO I3–I4

Create the collection, embed and add

A Chroma collection is like a table: each row holds an id, the chunk text, and its embedding. In build_index(), replace collection = ... and the bare ... below it. You need to:

Do thisWhy
Start a persistent Chroma client at DB_PATH.A persistent client writes to the chroma_db/ folder instead of keeping everything in memory. This is what survives a restart.
Delete any old collection first.Running ingest twice would otherwise collide with the ids already stored. Deleting and rebuilding makes "run it again" always safe, for example after you edit the documents.
Create the collection with cosine distance.Cosine compares the direction of two vectors (their meaning) and ignores their length. It matches the similarity you computed in Colab.
Embed with normalize_embeddings=True.Same as Colab: every vector gets length 1, so similarity scores are comparable across questions. You'll rely on that in homework Exercise 1.
Add with ids chunk_0, chunk_1, …Every row needs a unique id. The chunks came from splitting, so there are no hand-made labels like "returns" anymore.
Nudge Level 1

The calls you need, in order:

  • chromadb.PersistentClient(path=str(DB_PATH))
  • client.delete_collection(name)
  • client.create_collection(name, metadata={"hnsw:space": "cosine"}). HNSW is the search index Chroma builds; "space" picks its distance measure.
  • embedding_model.encode(list_of_texts, normalize_embeddings=True)
  • collection.add(ids=..., documents=..., embeddings=...), three lists of equal length.
Bigger hint Level 2

delete_collection raises an error if the collection doesn't exist yet (the very first run), so wrap it in try / except Exception: pass. encode() returns a NumPy array and Chroma wants plain lists, so call .tolist().

Exercise 1

Edge-case handling: know when to refuse

Goal: an out-of-scope question (e.g. "What's the weather like today?") should always get a refusal, and it shouldn't depend on the model choosing to say "I do not know".

Constraints: the refusal must be deterministic: the same out-of-scope question always refuses, and the generator is never called.

Deliverable: in your README (or homework/exercise1_notes.md), at least 2 in-scope and 2 out-of-scope questions with the bot's response to each, after your fix.

Nudge Level 1

retrieve() already returns a similarity for every hit (the CLI only prints the ids). Print the top similarity for a few questions. What do those numbers look like for questions the knowledge base can't answer?

Bigger hint Level 2

Decide before calling the generator whether retrieval found anything relevant enough. Run a batch of in-scope and out-of-scope questions, print the top similarity for each, and look for the gap between the two groups.

Don't copy a threshold from anyone. The method is the point, and your number will shift if your documents change. Include a few tricky out-of-scope questions that share words with your docs, because those are what catch a threshold that's too low.

Won't count

Hardcoding strings from the example questions (e.g. if "weather" in question), or relying on the prompt instruction alone.

Exercise 2

Multi-source RAG: policies and prices

Goal: the same chatbot answers policy questions and price questions from homework/model_prices.xlsx (columns model and price_thb), and still refuses things that are neither.

Nudge Level 1

Embeddings work on sentences, not spreadsheet cells. What would a table row look like as a sentence a customer could be answered with?

Bigger hint Level 2
  • Use pandas.read_excel and turn each row into a natural-language sentence before embedding.
  • Keep one collection. Record where each item came from in metadatas.
  • Reuse your Exercise 1 refusal, so questions neither source covers are still refused.
  • Then test its limit: ask the price of a product that isn't in the table, e.g. "How much is the LumaBox X999?", and print the top similarity. A neighboring product's price row can score well above your threshold, because to the embedding model "X999" means almost the same as "X200". Report honestly what your bot does. The Challenge exercise is about this exact weakness.
Won't count

Two collections with your own "does this look like a price question?" routing, or no refusal at all for questions neither source covers.

Deliverable: in your notes, at least one price question, one policy question, one question neither source covers, and the unknown-product price question, with the bot's response to each.

Challenge

Exact model names and serial codes (optional)

Goal: ask for the price of each LumaBox model, and a few serial codes like LMX-201. You'll find some come back with a sibling product's price.

Deliverable: first, a short written plan that explains why embeddings do this. Then a fix that uses a genuinely different retrieval mechanism.

Nudge Level 1

Codespaces fallback

If your laptop can't run the project, GitHub Codespaces gives you VS Code in the browser on a cloud machine. The project's .devcontainer folder installs the libraries and downloads the models for you. You need a free GitHub account.

  1. Open the project folder in VS Code on your laptop (VS Code itself only has to run, not Python).
  2. Open the Source Control panel and click Publish to GitHub. Choose a private repository and sign in when asked.
  3. On the new repository's GitHub page, click Code → Codespaces → Create codespace on main.
  4. Wait while it builds (5–10 minutes the first time). It's ready when the terminal shows All checks passed.
  5. Carry on with the guide in the browser. Skip the venv steps, because Codespaces installs everything globally. Publishing already created the repository and a first commit, so in Module 2 start from Step 2.

When Streamlit starts in Module 7, Codespaces offers to open port 8501 in your browser.

Progress is stored only in this browser.
