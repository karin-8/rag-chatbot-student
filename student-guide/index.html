RAG in 30 seconds

A small language model doesn't know LumaBox's policies, and if you ask it anyway it will guess. Retrieval-augmented generation fixes that in two stages:

  1. Prepare once. Cut the documents into chunks and turn each chunk into an embedding, a list of numbers that captures its meaning. Store the embeddings.
  2. Answer each question. Embed the question the same way, find the stored chunks whose embeddings are closest (the most similar meaning), paste those chunks into the prompt as context, and let the model answer from that context.

You built exactly this in Week 5 in a notebook. Today the embeddings move from a NumPy array in memory to a database on disk, and the code around the model grows up.

Colab vs real software

Colab

  • Ephemeral and linear
  • No version history
  • One global blob of state
  • Checked by eye
  • Shared by sending a copy

Real software

  • State survives a restart
  • Versioned: code, prompts, knowledge
  • Modular, with rules enforced in code
  • Tested automatically on every change
  • Shipped by a pipeline, then monitored

Chunk the raw text

A chunk is the unit retrieval hands back. When a question comes in, the bot pastes whole chunks into the prompt, so each chunk should be a self-contained piece of evidence.

  • Too big (the whole file): every question retrieves everything, the embedding becomes an average of unrelated topics, and you blow the model's 512-token prompt limit.
  • Too small (one line each): the line "Available 24/7, every day." gets separated from its heading, "Technical Support", and on its own it doesn't say what is available.

This file has a clear structure, one policy per paragraph, so splitting on that structure gives ideal chunks. For long unstructured text (a PDF manual, say) the usual fallback is fixed-size chunks of a few hundred words with some overlap between neighbors.

Open data/policies.txt and look at its shape. Then fill in chunk_documents() so it returns a list of chunk strings:

  • Policies are separated by blank lines.
  • Strip whitespace from each piece.
  • Drop the title line at the top. It's a heading with no body.

A Chroma collection is like a table: each row holds an id, the chunk text, and its embedding. In build_index(), replace collection = ... and the bare ... below it. You need to:

Do thisWhy
Start a persistent Chroma client at DB_PATH.A persistent client writes to the chroma_db/ folder instead of keeping everything in memory. This is what survives a restart.
Delete any old collection first.Running ingest twice would otherwise collide with the ids already stored. Deleting and rebuilding makes "run it again" always safe, for example after you edit the documents.

Nudge Level 1

The calls you need, in order:

  • chromadb.PersistentClient(path=str(DB_PATH))
  • client.delete_collection(name)
  • client.create_collection(name, metadata={"hnsw:space": "cosine", "kb_version": KB_VERSION}). HNSW is the search index Chroma builds; "hnsw:space" picks its distance measure.
  • embedding_model.encode(list_of_texts, normalize_embeddings=True)

Module 2 · 35–60 min

Building the agent Required

An agent is more than a model call. It's a model plus the instructions it gets (the prompt) plus the rules it must follow no matter what (the policy). Both need the same care as code.

Outcomes

  • The prompt lives in a versioned file, and every answer records which version produced it.
  • See what happens to a bot whose policy exists only in its prompt.
  • Enforce the scope policy in code, and run the CLI: python -m src.main answers questions.

2.1 · System prompt & prompt versioning

A one-word change to a prompt can change the bot's behavior as much as a code change, so practitioners treat prompts as code:

  • In a file, not buried in a function. A prompt change then shows up in git diff and gets reviewed.
  • Versioned, never edited in place. prompts/answer_v1.txt, answer_v2.txt, … plus PROMPT_VERSION in src/rag.py naming the live one. Rolling back is a one-line change.
  • Recorded with every answer, so when a customer reports a bad answer you know which prompt said it.
  • Released only through a gate that compares the new version with the old one on the same test questions (Module 3.2).

Module 3 · 60–85 min

Testing the agent

You wouldn't sign off a subsystem without checking it meets spec. For an AI system the spec is a set of questions with the outcome each must produce, and the checks run automatically on every change.

Test it: pytest, must pass 100%

  • The deterministic parts: did retrieval bring back the evidence? Did the policy refuse what it should, and only that?
  • Same input, same result, every time.

Evaluate it: the quality gate

  • The generated answers, whose wording is fuzzier.
  • Measured as a pass rate per category, and compared with the last accepted version.

Outcomes

  • A golden dataset covering every policy, with paraphrased questions.
  • pytest passes: retrieval evidence and policy decisions for every golden question.
  • A committed quality-gate baseline, and proof that the gate rejects prompt v2.

3.1 · QA: building the golden dataset

A test for one phrasing of one question isn't enough. Real customers ask every question a dozen ways, and every change you make (new documents, different chunking, another prompt) can quietly break some of them. Writing a test function for each would never end.

A golden dataset turns the tests into data: a curated list of questions, each with the outcome it must produce. One test function runs every row. Teams building production chatbots keep one under version control, have the people who know the content help write it, and run it after every change to code, prompt, model or knowledge. A common rule is "don't ship a change that lowers the pass rate", often with a launch bar such as 95%.

Open tests/golden.json. It has three rows. Here's the first:

FieldMeaning
id, categoryA unique name for the row, and its topic. Failures print the id; the gate reports pass rates per category, so you see which kind of question is weak.
questionThe canonical question, phrased close to the source.
variantsParaphrases, written the way real users type. Every variant is a test case. This is what makes the dataset valuable: it tests understanding of meaning, not one exact sentence.
must_includeShort facts, copied exactly from data/policies.txt, that the evidence (and ideally the answer) must contain.
expected_action"answer" if the bot should answer from the documents, "refuse" if the question is out of scope (POLICY.md P1).
known_issue (optional)A failure you've investigated and decided to keep, with the reason. Look at the third row, out_of_scope_tricky: it's the "ship to the moon" gap from Module 2.2, written down as a test.

When a variant fails

The message shows which chunks came back, for example retrieved ['chunk_0', 'chunk_4'], but they don't contain ['8 business days'], or the score that was wrongly refused. First ask: is this a fair question a real customer could ask? If not, fix the row. If it is, you've found a real weakness. Don't reword the question until it passes. Deleting or softening failing cases makes your tests meaningless.

Instead, keep the row and record what you learned in a "known_issue" field, as the out_of_scope_tricky row does. Pytest then reports it as xfail, and tells you if it ever starts passing.

  • The gate exits with an error code, which is how a pipeline knows to stop. This exact command runs in CI in Module 4.

Module 4 · 85–100 min · Read and trace

Production: CI/CD

Everything so far ran on your laptop. In a real team, nobody copies code onto the production server by hand. A change goes through an automatic pipeline that tests it, packages it and ships it, and stops it the moment a check fails. That pipeline is the safety gate between your keyboard and a customer.

Nothing to build today

Building containers and running pipelines needs Docker and a CI service, so in this module you read the two files that define them and trace what would happen. Both files are in your project and are real, working configurations. Pushing to GitHub to watch them run is the homework challenge.

Outcomes

  • Explain what happens between git push and a customer seeing a change.
  • Read a Dockerfile and a CI/CD workflow, and connect each step to the module that built it.
  • Predict which step would stop a bad change, such as prompt v2.

The flow

Some precise terms, because they're often mixed up:

TermMeaning
RepositoryWhere you push code. The push (or pull request) is what triggers the pipeline. That's why git matters even if nobody looks at your history.
Container imageThe packaged app: your code plus the exact Python, libraries, model weights and knowledge base, frozen together. The pipeline builds it; you don't push code into it.
CIBuild and test every change automatically, and reject what fails. For AI systems that means two kinds of check: fast deterministic tests, and an evaluation gate on the golden dataset.
CDShip the image that passed: usually to staging first, then to production gradually (a few users, then everyone), with a way to roll back.

Why bother? Safety: a bad prompt or broken retrieval is stopped before customers see it. Reproducibility: the image that passed the tests is byte-for-byte the one that ships, so "it worked on my machine" stops being an excuse. Rollback: every image is tagged with its commit, and every answer logs its prompt and knowledge versions, so undoing a bad release is quick and certain.

Step 1

Read the Dockerfile

Open Dockerfile. It's a recipe for the container image, read top to bottom. Each instruction adds a layer.

Check your understanding:

Why download the model weights while building the image, not when the app starts?

So every container starts instantly and identically, with no network dependency. A server that has to fetch 1 GB on startup is slow to scale, and fails if the download site is down. The same reason the setup check downloaded the models before class.

Why is requirements.txt copied and installed before the code?

Docker reuses a cached layer if nothing it depends on changed. Libraries change rarely and take minutes to install; code changes constantly. Installing them first means a code change only rebuilds the last, fast layers.

Which files never get into the image, and why?

Everything in .dockerignore: your .venv (the image installs its own), chroma_db (rebuilt inside by src.ingest), logs (private user data), .git, and tests and homework (not needed to run the bot).

Step 2

Read the pipeline

Open .github/workflows/ci.yml. This is a GitHub Actions workflow. YAML is just nested settings: indentation matters, and - starts a list item.

Everything in it is something you did today, automated:

Trace three changes through the pipeline

For each change, decide which job and step stops it (if any), and what customers end up with. Then open the answer.

A. A teammate sets PROMPT_VERSION = "v2" and pushes to main.

test runs: install, ingest and pytest pass (pytest doesn't look at generated text). The quality gate fails: out of scope and refund drop below the committed baseline, and the gate exits with an error. build and deploy never start. Customers keep getting v1. B. Someone edits data/policies.txt and accidentally deletes "24/7".

Every check passes, the image is built, and the change is deployed: probably automatically, or after one approval click if the production environment requires it. Most changes should flow through this quickly. The gate only gets in the way of changes that make things worse.

D. v1 shipped, and a week later it turns out to be wrong for some new kind of question. How do you roll back or fix?

Same road as every change: add the new questions to the golden dataset (they fail), fix the prompt as a new version or fix the knowledge, check the gate locally, push. If an old image was better, redeploying it by its commit tag is a rollback. Never patch production by hand: then the running system no longer matches any tested version.

Three parts:

  • The summary: refusal rate, latency, and which prompt and knowledge versions were live. A jump in refusal rate right after a deploy is a classic early warning.
  • Flagged turns: refused, the model declined, low confidence (answered, but barely above the threshold), or negative sentiment. Read every one.
